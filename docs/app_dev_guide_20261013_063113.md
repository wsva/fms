# Dataset Hub — website implementation, and what to build on the app side

Audience: the agent working on `learning/fms-app` (Tauri + Rust + SQLite).
Read this once, then implement §7 in order. Every contract below is what the
website **actually returns today** (verified against a production build, see §8),
not what the app's own `sync/rest.rs` returns. Where the two differ, this document
says which side changes.

Repo paths:
- **website** = this repo (`fms/node_project`, Next.js 16 App Router, Prisma + Postgres).
- **app** = `learning/fms-app/src-tauri/` (gitignored here; reference only).

---

## 0. TL;DR

The website is now a **hub** for self-contained dataset directories
(`<datasets>/<type>/<uuid>/` with `info.json`, `data.sqlite3`, `media/`, `waveform/`).

Already done on the website (do not re-implement):
- `POST /api/dataset/upload` — accepts a tar.gz of a dataset dir, stores an
  immutable per-version archive plus an extracted live copy, parses `info.json`
  into a Postgres catalog.
- `GET /api/v1/datasets`, `GET /api/v1/datasets/{uuid}/manifest`,
  `GET /api/v1/datasets/{uuid}/snapshot`, `GET /api/v1/file` — the hub read
  contract, byte-compatible with `sync/rest.rs` hashes and headers.
- `GET /api/card/sync/pull`, `POST /api/card/sync/push` — already speak the shape
  `datasets/cards/sync.rs` expects, on the origin `auth::BASE_URL`.
- Market / detail / upload / manage pages for humans. Subscribing to a `shared`
  dataset is a **browser-only** action today (§T4).

To do on the app side (§7):
1. Make the hub client able to talk to the **website** origin with
   `Authorization: Bearer <access_token>` instead of the PC device-HMAC headers.
2. Add a **dataset export + upload** command (the app can currently only pull).
3. **Feature-detect** and skip the hub endpoints the website does not implement
   (§6) instead of failing the sync round.
4. Keep card sync as-is; verify cursor + LWW behaviour (§8.6).

## 1. Topology and authority rules

```
 desktop app  ──(A) LAN hub: app-as-server, device HMAC──►  another app instance
     │
     └──────(B) website hub: OAuth2 Bearer / cookie──►  this repo
                                                      ├─ Postgres: catalog, subscriptions, tags, auth
                                                      └─ disk: $DATASET_ROOT (default /fms_datasets)
                                                            <type>/<uuid>/            live extracted copy
                                                            _archive/<type>/<uuid>/v<N>.tar.gz
                                                            _tmp/<upload-uuid>/       staging sandbox
```

Authority rules — these decide who wins any disagreement:

| Fact | Authority | Consequence for the app |
| --- | --- | --- |
| dataset `uuid`, `type`, `format`, `name`, `description`, `language`, `spec`, `extra` | `info.json` inside the uploaded archive | You may rewrite these locally; they land in the catalog on next upload. |
| dataset **ownership** (`user_id`) | website Postgres | `info.json.sharing.owner_id` is **ignored** on upload. The upload caller becomes owner. |
| dataset **visibility** (`private\|shared\|public`) | website Postgres | `info.json.sharing.visibility` is **always ignored**. The `visibility` form field is honoured on the **first** upload of a uuid only; later uploads keep the stored value, and only the manage page / `setDatasetVisibility` changes it. |
| **subscriber list** | website Postgres | `info.json.sharing.subscribers` is a mirror the app may display, never a control. The website never rewrites `info.json` (see §4.3), so a stale subscriber list can stay in the file. |
| card/tag rows | the dataset's own `data.sqlite3`, LWW by `updated_at` | Rows never enter Postgres. |
| per-file hashes / `overall_hash` | recomputed by the website from the live dir | Your local manifest must match it; if not, §4.1. |
| snapshot sequence (`snapshot_seq`) | website catalog, monotonic | Your sync cursor for file-level changes. |

Storage choice ("catalog + blob"): the website deliberately does **not** import
`data.sqlite3` into its own tables. It serves the DB to followers as bytes
(snapshot) and as rows (card sync). So the app remains the only place where card
content is queried.

## 2. Identity: how the app must authenticate

The website accepts three transports, resolved in this order
(`src/lib/datasets/auth.ts`, `src/lib/oauth2.ts`, `src/lib/api-auth.ts`):

1. `Authorization: Bearer <access_token>` — OAuth2 access token minted by
   `POST /api/oauth2/signin` (what `auth.rs` already does for card sync).
   Verified against `OAUTH2_RSA_PUB_FILE`, must exist in `oauth2_token` and the
   user must be `is_active='Y'`. **This is what the app should use.**
2. `access_token` **cookie** — same token, for browsers.
3. `x-api-key: <raw key>` — sha256 looked up in `settings_api_key`; carries a
   `scope` of `read` or `write`.

Identity unification: in this schema an `oauth2_token.user_id` **is** the email,
and `settings_api_key.user_id` is the email too. All three paths resolve to the
same principal string.

Access matrix (which identity gets what):

| Endpoint | anonymous | read-only api-key | write api-key | Bearer / browser session |
| --- | --- | --- | --- | --- |
| `GET /api/v1/datasets` | sees `public` only | sees public + own/subscribed | same | same |
| `GET .../manifest`, `.../snapshot`, `/api/v1/file` | `public` only | yes (public + subscribed + own) | yes | yes |
| `GET /api/card/sync/pull` | `public` only | yes | yes | yes |
| `POST /api/card/sync/push` | 401 | **403** | yes | yes |
| `POST /api/dataset/upload` | 401 | **403** | yes | yes |

Visibility gate for every read (`src/lib/datasets/access.ts::canReadDataset`):
`public` → anyone (incl. anonymous); `shared` → owner or subscriber;
`private` → owner only. A gate failure returns **401 when the caller is
anonymous, 403 when identified** — treat 401 as "attach a token and retry",
403 as "this account cannot see it".

> The website has **no** device pairing and does **not** read
> `x-fms-device/-ts/-sig/-role/-cluster/-protocol`. Sending them is harmless but
> useless; not sending them is required for anything but `GET /api/v1/datasets`
> style anonymous reads (§7.1).

## 3. Endpoint contracts

All routes are `dynamic` (never cached at build). Every JSON error body is
`{ "error": "<message>" }`. `Content-Type: application/json` unless stated.

### 3.1 `GET /api/v1/datasets[?lite=1]`

Returns a **bare JSON array** (not an object). Fields are the app's contract
(`sync/rest.rs::datasets_list`).

```json
[{ "uuid": "…", "name": "…", "updated": "2026-10-13T06:31:13Z",
   "dataset_type": "card", "media_count": 412, "status": "ready" }]
```

- Ordered by `uuid` ascending.
- Only rows with `deleted='N'` **and** `status='ready'`, and only those the
  caller may read. A `shared` row appears **only if the caller subscribes** (or
  owns it). So the list is already filtered — do not post-filter by visibility.
- `updated` = `info_updated_at` if present, else the row's `updated_at` as an ISO
  string. This is the same string the app writes into `info.json.updated_at`.
- `?lite=1` sets `media_count` to `0` — the incremental round never uses counts,
  so use `lite=1` for the periodic catalog poll.
- For `dataset_type == "card"`, `media_count` carries the **card count**, not a
  media count (the app's own convention).

### 3.2 `GET /api/v1/datasets/{uuid}/manifest`

```json
{ "file_count": 137, "total_bytes": 312345678, "overall_hash": "<sha256 hex>",
  "updated_at": "2026-10-13T06:00:00Z", "dataset_type": "card",
  "files": { "info.json": "<sha256 hex>", "media/a.mp3": "<sha256 hex>" } }
```

- `total_bytes` is a JSON **number** (safe for `as_u64`), `file_count` number.
- `files` keys are forward-slashed rel paths, relative to the dataset root — the
  same keys your own `compute_manifest` produces.
- `updated_at` is `""` if the catalog has no `info_updated_at`.
- The DB and its sidecars are **absent** from `files` (§4.1).

### 3.3 `GET /api/v1/datasets/{uuid}/snapshot`

One `application/gzip` body: the whole dataset directory as tar.gz with
**rel-path entries and no top-level directory** (`info.json`, `data.sqlite3`,
`media/…` at the archive root — same as `rest.rs::snapshot`).

Response headers you must record:

| Header | Meaning |
| --- | --- |
| `x-snapshot-hash` | equals the manifest `overall_hash`; store it as "this dir is at hash X". |
| `x-snapshot-seq` | decimal integer, the catalog change cursor; store as your resume point. |
| `Content-Disposition` | `attachment; filename="<uuid>.tar.gz"` |
| `Content-Type` | `application/gzip` |
| `Cache-Control` | `private, no-store` — never serve a cached snapshot to a second caller. |

- No `Content-Length`: the body is streamed, and the archive is re-packed per
  request. Do not assume you can resume a partial snapshot; re-request.
- Inside the tar: `data.sqlite3` is the **frozen** copy (SQLite backup API,
  `journal_mode=DELETE`). `-wal`, `-shm`, `fts5.sqlite3*` are **excluded**.
  Note the asymmetry with §3.2: the snapshot *includes* the DB, the manifest
  *excludes* it.
- Concurrent packs are capped (`MAX_CONCURRENT_SNAPSHOTS`, default 2); over that
  a request waits rather than failing, but nginx may time out a very large pack —
  see §9.

### 3.4 `GET /api/v1/file?dataset=<uuid>&path=<rel>`

Serves one **non-DB** file, Range-aware.

- `200` whole file, or `206` with `Content-Range: bytes s-e/total`,
  `Accept-Ranges: bytes`.
- `416` with `Content-Range: bytes */total` for an unsatisfiable range.
- Range parsing: `bytes=START-END`, `bytes=START-`, and suffix `bytes=-N`
  (N = **length from the end**, not an offset) are honoured; multi-range is
  ignored → treated as a whole-file 200.
- `403` when `path` is `data.sqlite3`, `data.sqlite3-wal`, `data.sqlite3-shm`,
  `fts5.sqlite3`, `fts5.sqlite3-*`, or escapes the dataset (checked with
  `realpath`, so symlinks out of the dataset are refused).
- `404` missing file / not a regular file / unknown dataset.
- CORS `Access-Control-Allow-Origin: *` is set (browser players need it).

### 3.5 `GET /api/card/sync/pull?dataset_uuid=&since=`

```json
{ "dataset_uuid": "…", "cards": [ … ], "tags": [ … ], "server_time": "2026-10-13T06:31:13Z" }
```

- `since` = the `server_time` from your previous pull. **Empty/absent `since`
  returns every live row** (first sync). Comparison is
  `updated_at > canonical(since)` on the fixed-width UTC text form, identical to
  your `get_local_changes`.
- `server_time` is taken **before** the read, so a row written mid-read is
  delivered next round rather than skipped. Persist it verbatim as your cursor.
- `cards[]` = `SyncCard` exactly as your `sync.rs` defines it:
  `uuid, question, suggestion, answer, note, familiarity, question_hash?,
  source_card_uuid?, source_dataset_uuid?, deleted_at?, created_at, updated_at`.
  A row with `deleted_at != null` is a **tombstone** — apply it, never purge it.
- `tags[]` = `uuid, name, color?, deleted_at?, created_at, updated_at`. Your
  client currently sends `tags: []` on push; pull **does** return tags, so handle
  them.
- `400` when the dataset is not `type=card`; `404` unknown/not-ready; 401/403 per §2.

### 3.6 `POST /api/card/sync/push?dataset_uuid=<uuid>`

Body: `{ "cards": [SyncCard…], "tags": [SyncTag…] }` (your `PushRequest`).
Response `200`:

```json
{ "accepted": 3,
  "conflicts": [{ "uuid": "…", "local_updated_at": "…", "remote_updated_at": "…", "winner": "remote" }],
  "server_time": "2026-10-13T06:31:13Z" }
```

- LWW per `uuid` on `updated_at`: strictly newer incoming row wins and is written
  as a **full-row upsert** (including `deleted_at`). Equal-or-older → skipped and
  reported as a conflict with `winner: "remote"`; you keep your local copy and
  should record the remote row from the next pull.
- `dataset_uuid` missing → `400`; non-card dataset → `400`; more than
  `MAX_CARD_PUSH_ROWS` (default 20000) rows in one push → `413`; pusher must own
  or subscribe the dataset → `403` (`canPushDataset`).
- A successful push bumps the catalog `snapshot_seq` and `updated_at`, so
  followers see the change on their next `?lite=1` list even though
  `overall_hash` did not move (§4.2).
- Writes serialize behind a per-dataset in-process lock; two devices pushing the
  same card cannot interleave, but a push is not retry-safe beyond the row CAS —
  see §5.

### 3.7 `POST /api/dataset/upload` (website-specific; no app-side equivalent today)

`multipart/form-data`:

| Field | Required | Notes |
| --- | --- | --- |
| `file` | yes | tar.gz of the dataset dir. Accepted layouts: `info.json` at archive root **or** exactly one directory down (so both `tar -czf x.tgz -C <uuid> .` and `tar -czf x.tgz <uuid>` work). |
| `visibility` | no | `private` \| `shared` \| `public`; anything else → `400`. Honoured **only when the uuid is new**; a re-upload keeps the visibility already stored (change it from the manage page). What `info.json.sharing.visibility` says is always ignored. Default `private`. |
| `tag_uuids` | no | repeated field or comma-separated; groups the dataset under existing `dataset_tag` rows. Grouping only, never a permission. |

Responses:
- `201` first upload, `200` new version of an owned dataset. Body:
  `{ "dataset": {…serialized catalog row…}, "version": N,
     "archive_sha256": "<hex of the upload itself>", "archive_size": "<decimal string>" }`.
- `400` — not multipart; unparseable form data; missing/empty `file`;
  no `info.json` at root or one dir down; invalid `info.json` (spec v2 rules);
  bad `visibility`.
- `401` anonymous, `403` read-only api key, `413` over `MAX_DATASET_UPLOAD_MB`.
- `409` — uuid already registered to another account; uuid registered but
  soft-deleted; declared `type` differs from the registered one.

Catalog row fields to note (`serializeDataset`): `archive_size`, `total_bytes`
and `snapshot_seq` are **decimal strings** (Postgres `BIGINT`, not JSON-safe as
numbers); `file_count`, `media_count`, `card_count`, `spec` are numbers;
`info_created_at` / `info_updated_at` are the `info.json` stamp strings or `null`.
`journal_role` is selected with the row but deliberately **never serialized** — it is an
internal sync fact (§6.3), and the conformance vector `live_edit_gate` fails if the
serializer ever starts emitting it.

Upload is also the one live-directory writer that is deliberately **not** role-gated: an
archive upload replaces the whole dataset, it is the owner's bootstrap and versioning
channel, and `journal_role` defaults to `mirror`, so gating it on `authority` would forbid
ordinary owner versioning of nearly every dataset. It stays owner-only (`409` when the uuid
belongs to another account). See §6.3 for the rule that governs *row-level* writes.

## 4. Parity invariants — the website mirrors the app; the app must not drift

### 4.1 Manifest hash recipe (`src/lib/datasets/manifest.ts`)

For every regular file under the dataset dir, excluding DB files, **sorted
byte-wise by forward-slashed rel path**:

```
overall_hash = sha256( concat over files: rel_path + 0x00 + sha256hex(file) )
```

- Excluded from the set: `data.sqlite3`, `data.sqlite3-wal`, `data.sqlite3-shm`,
  `fts5.sqlite3`, `fts5.sqlite3-*`.
- Sort is UTF-8 byte-wise (`Buffer.compare`), matching Rust `str` `Ord`. If you
  ever sort with a locale-aware or char-wise comparator in a non-ASCII dataset,
  hashes diverge.
- Verified equal to the app's own `compute_manifest` on a real dataset
  (`c38cd1f5…` matched across catalog, manifest, and a re-extracted snapshot).
  **Any future change to this recipe on either side is a breaking protocol
  change.** If you find a mismatch, stop and report; do not "fix" your local
  hash to agree.

### 4.2 DB churn must not dirty the hash

`overall_hash` excludes the DB by design. Consequences you can rely on:
- Editing a card row changes **nothing** in the manifest; followers converge via
  §3.5/§3.6, not by re-downloading media.
- Adding/altering one byte of any non-DB file (incl. `info.json`) changes
  `overall_hash` and triggers a re-pull.
- Therefore: never write runtime state into a non-DB file inside the dataset dir
  (no `.DS_Store`, no local `sync.json`, no cache). Put local state in the app DB.

### 4.3 `info.json` is never rewritten server-side

Because it is part of the hashed set, rewriting it on subscription would churn
`overall_hash` and force every follower to re-pull. The website therefore leaves
the file exactly as uploaded and keeps ownership/visibility/subscribers in
Postgres only. So:
- Do not expect the downloaded `info.json` to reflect current subscribers.
- Do not start writing subscriber data into `info.json` "to make it true".

## 5. Limits, and what to do when you hit one

| Knob | Default | Effect on the app |
| --- | --- | --- |
| `MAX_DATASET_UPLOAD_MB` | 512 | archive size cap (checked on `Content-Length` **and** streamed bytes). Split or trim before uploading. |
| `MAX_EXTRACT_MB` | 4× upload cap | extracted total bytes; a gzip bomb is refused with 413. |
| `MAX_DATASET_ENTRIES` | 20000 | file entries in the archive. |
| `MAX_CARD_PUSH_ROWS` | 20000 | rows per push → `413`. Batch your local changes. |
| `MAX_CONCURRENT_SNAPSHOTS` | 2 | packs queue; a big dataset can make a caller wait. |
| `SNAPSHOT_PACK_TTL_MS` | 30 min | abandoned staging dirs are cleaned after this. |

Rejection patterns you will see: archive errors surface as `413` when the
message matches `/limit|exceeds|unsafe archive/`, otherwise `500` with the raw
message. Retry only on 5xx/429/network; **never** retry a `409` or `403` with the
same payload.

Push is not idempotent in the sense of a request key: it is a per-row CAS on
`updated_at`, so re-sending the same batch is safe (rows you already won come
back as `winner: "remote"` conflicts). Read that as "no-op", and do not surface
it as a user-visible conflict for rows you just pushed.

## 6. Hub endpoints the website does NOT implement

`sync/rest.rs` serves these; the website returns `404` (Next.js unmatched route,
JSON-less or `{error}` body). Callers must **feature-detect and degrade**, not
fail the round:

| Path | App caller today | Required behaviour against the website |
| --- | --- | --- |
| `GET /api/v1/status` | `pc_check_status`, `hub_protocol_version` | treat as "no protocol advertisement"; assume hub protocol = the version this doc describes. |
| `GET /datasets/{uuid}/changes`, `GET /app/changes`, `GET /app/state`, `POST /sync/changes` | `pc_changes_since`, `pull_app_scope`, `backfill_app_history`, writeback | **Now implemented** — the website hosts the row journal these need. See §6.1 for the parity caveats. |
| `POST /pair/request`, `GET /pair/status` | `pc_pair_start`, `bind_cluster_after_pairing` | Pairing is a LAN concept; a website origin is authenticated by OAuth2, so disable the pairing UI path for it. |
| subscribe / unsubscribe a dataset | — | No REST route; browser server actions only (§T4). |
| `GET /chat/messages`, `/chat/attachment/{uuid}` | chat features | unavailable against the website. |
| `GET /wiki/datasets`, `/wiki/dataset/{dir,file,search}` | wiki hub browsing | unavailable; browse wiki datasets locally only. |

Also absent by design: cluster/role concepts (`x-fms-role`, `x-fms-cluster`) and
device identity — the website's principal is an account, not a device.

### 6.1 The row journal + `app/state` are live (protocol v6)

The website now runs the `@app` row journal and the four-table
`GET /api/v1/app/state` (`dictation`, `xp`, `reviews`, `attempts`, each paged by
rowid with its own cursor, `lifetime_xp` recomputed as `SUM(amount)`), and `/stats`
renders the same projection. A website origin therefore supports journal-driven
incremental convergence and `backfill_app_history` — the Android thin-client
incremental story is a supported path, not new website work.

Honest caveats that still apply:

- **Practice-plane events are insert-once.** `read_attempt_event` /
  `card_review_event` converge by set equality on their dedup keys, never by
  re-execution — a replayed event is a no-op.
- **`dataset_journal` is advertised only when an authority dataset is hosted here.**
  A pure mirror origin does not mint dataset-scope journal seq (INV-1).
- **The `@app` events half of the backfill is gated at `protocol >= 6`** — the
  website advertises v6, so a current app receives `reviews` and `attempts`; an
  older client does not.

### 6.2 The inbox: producer, optimistic `live/` write and the ack consumer (§8.3 steps 1–3)

`POST /api/v1/inbox`, `GET /api/v1/inbox?scope=&after=` and
`POST /api/v1/inbox/ack` shipped in phase 5 with **nothing writing into them**, so
the surface was only reachable by hand-curl. That changed: the website UI now has a
dataset-card editor that proposes card **and tag** edits.

- **Where:** `src/lib/datasets/card_proposals.ts` (the seam) called by
  `src/app/actions/card_editor.ts`, surfaced at `/dataset/card/<uuid>` (cards in
  `client.tsx`, tags in `tags.tsx`). The live-side pieces are
  `src/lib/datasets/ack_rollback.ts` (the pure winner decision) and
  `applyDatasetChangeIfStale` in `src/lib/sync/datasetjournal.ts` (the guarded applier);
  the consumer is `src/app/api/v1/inbox/ack/route.ts`.
- **What it proposes** — the **full five dataset-scope card-family kinds** §14 phase 5
  targets (cards *and* tags, per §15 q1), each exactly as the app's card command path
  journals it (`datasets/cards/mod.rs`), so the drainer reuses that command verbatim
  (INV-18). `edit_time` is canonical fixed-width UTC (INV-6).

  | kind | op | object_id | payload |
  | --- | --- | --- | --- |
  | `card_save` | `upsert` | `payload.uuid` | the serialized `Card` (snake_case) |
  | `card_delete` | `delete` | `payload.card_uuid` | `{card_uuid}` |
  | `card_tag_save` | `upsert` | `payload.uuid` | the serialized `Tag` — `uuid`, `name`, `color`, `deleted_at`, `created_at`, `updated_at` (both nullables sent explicitly) |
  | `card_tag_delete` | `delete` | `payload.tag_uuid` | `{tag_uuid}` |
  | `card_set_tags` | `upsert` | `payload.card_uuid` | `{card_uuid, tag_uuids[]}` |

  `card_review` is **not** proposed: it is `@app`-scope and already journalled, so it
  never enters the dataset-scope inbox.
- **`card_set_tags` is a whole-set replace, never a delta.** The editor sends the card's
  ENTIRE desired tag list; the appplier soft-deletes the card's live pairs and re-inserts
  exactly that list, so a tag missing from the array is a tag being removed. A caller
  that computes a delta silently erases everything left out. Because `object_id` is the
  `card_uuid`, the whole pair set is one coalescing unit: two assigns to the same card
  fold to the later one, and a replay re-derives the same live set from the same payload.
- **Card↔tag links are now readable** via `cardstore.getCardTagLinks(dir)` — the live
  joins, filtered to pairs whose row *and* tag are un-tombstoned (the app's live-view
  predicate). `getChangesSince` still returns only `card` and `tag` rows: its shape is
  the frozen `/api/card/sync/pull` wire.
- **Tag liveness is a staleness gate, not a guarantee.** The website checks the proposed
  ids against its own live copy before queueing, but a `card_tag` join is plain TEXT and
  neither applier rejects a dangling tag, so an id deleted on the hub after the check
  still drains. Treat the set as authoritative, re-read it after the drain, and never
  present a queued assign as confirmed.
- **Scoped to mirrors only.** The editor is enabled for `journal_role='mirror'`
  datasets; for an `authority` dataset a row edit rides
  `POST /api/v1/sync/changes` and journals directly, so the UI refuses and says so.
- **`live/` is written optimistically, after the queue commits (§8.3 step 1).** The order is
  load-bearing and is the opposite of "write, then propose": a live write that fails *after*
  the proposal committed is the safe direction — the mirror keeps the authoritative row, which
  is exactly what a rejection would have produced, and the read-path sweep below re-derives the
  lost write. A write *before* the queue would strand a mutation no ack will ever correct. The
  write is additionally gated on `queued === 1` (`deduped` ⇒ it was already written once;
  `refused` ⇒ there is nothing to write).
- **The optimistic write is GUARDED, not unconditional.** It goes through
  `applyDatasetChangeIfStale(dir, kind, payload, stamp, guardEditTime)`
  (`src/lib/sync/datasetjournal.ts`), not the authority path's `applyDatasetChange`. The guard
  reads the target row's stored `updated_at` inside the SAME `withDatasetLock` scope as the
  write and applies only while the row is absent or `stampsCmp(stored, edit_time) <= 0` —
  "nobody has touched this row since the edit was made". Anything newer, or a stored stamp this
  host cannot parse, returns `superseded`; a mirror whose `data.sqlite3` was never reconciled
  returns `not-ready` and the directory is never created (`openCardDb` would otherwise
  fabricate a schema into a dataset that has no rows). This is a deliberate deviation from
  "just reuse the authority applier": a website edit and a hub row arriving through
  `/api/card/sync/push` race for the same row, and only a guard keeps the loser from clobbering
  the winner.
- **The ack consumer exists (§8.3 steps 2–3, INV-4).** `recordAck`
  (`src/lib/sync/inbox.ts`) now `RETURNING`s the rows its `status='pending'` guard actually
  transitioned and returns them as `flipped`, and `POST /api/v1/inbox/ack` rolls each newly
  rejected flip back to the hub's winner *after* the PG transaction commits (file IO stays
  outside the tx, the same ordering `/api/v1/sync/changes` uses). Because a flip happens
  exactly once, a re-ack yields `flipped: []` and rolls back nothing — that is the whole
  idempotency argument, no "was this applied" column needed. `accepted` flips are NOT
  re-applied here (the producer already wrote them); the response wire is unchanged, still
  `{accepted, rejected, unknown}`.
- **Naming the winner: `winner_kind` first, payload shape second.**
  `winnerToApply` (`src/lib/datasets/ack_rollback.ts`) takes the hub's own
  `rejected[].winner_kind` (additive on the wire; `sync/inbox.rs` sends it, `rest.rs` omits it
  for a tombstone drop) and trusts it only when it names a writable kind in the proposal's
  family AND the payload is coherent with that name — a named `card_delete` over a full-Card
  payload is refused rather than executed, because an accidental delete is the one
  unrecoverable mistake. With no name it shape-detects, in this order: `tag_uuids[]` →
  `card_set_tags`; `question` + `answer` → `card_save` (payload passed through verbatim, it IS
  the authoritative row); `name` + `uuid` in the tag family → `card_tag_save`; a single locator
  key → the family delete keyed by the proposal's `object_id`; `winner_seq 0` with a null
  payload (or the NULL `recordAck` stores for it — `asIntGE1` accepts only ≥ 1) → the family
  delete. Anything unrecognized returns `null`: the verdict is recorded, the live row is left
  alone, and the UI says so. `winner_kind` is threaded onto the flip for this round only —
  `app_inbox` has no column for it, so the read-path sweep decides from the stored payload's
  shape, which is the same answer whenever the shape is distinguishable. The `inbox_ack`
  vector pins that no such column exists, so adding one is a visible, deliberate change.
  The stamp written is the winner's own `updated_at` when it carries one, else the rejected
  proposal's `edit_time` (guaranteed ≤ any later accepted row, which is what keeps the guard
  sound above).
- **A rollback refreshes counts and NEVER bumps `snapshot_seq`.** `refreshCardCounts` recomputes
  `card_count` (and `updated_at`) only. For a hosted scope the honest subscriber cursor is the
  hub's journal seq; counting both a catalog counter and the journal would recreate §3 fact 2 —
  the same rule `/api/v1/sync/changes` applies to its own writes. (The `snapshot_seq` bump in
  `api/card/sync/push` is the *legacy subscriber-pull* channel, not this one.)
- **Consequence for subscribers, stated plainly:** `snapshot.ts` freezes
  `live/data.sqlite3` per request (`backupDb`), so an optimistic edit CAN be packed into a
  snapshot a subscriber downloads before the hub's verdict arrives, and the rollback then lands
  as a following change. That is what §8.3 step 1 accepts on the website's own behalf: the row
  is the website's copy, the hub stays the authority, and a rejected edit is rolled back rather
  than left standing.
- **The read-path self-heal sweep.** An fs failure after a *terminal* verdict can never be
  re-acked (the row is no longer `pending`), so `getProposalOutcomes` re-derives the same two
  calls on every editor read — a rejected verdict through `winnerToApply`, an accepted one
  through its own payload (an idempotent re-write, so a lost optimistic write lands). Applied-ness
  is derived from the live row's stamp versus the proposal's `edit_time`, which is exactly what
  the guard already checks, so no schema column is added. A `card_set_tags` rollback whose tag
  rows the mirror does not have yet fails on the `card_tag` foreign key: the route logs it and
  keeps the durable verdict, and the next editor read retries the same write.
- **UI.** `/dataset/card/<uuid>` shows a **Recent outcomes** panel next to the pending list
  (`client.tsx`; tag toasts in `tags.tsx` report `appliedLocally` as "shown locally"), with one
  label per verdict-and-heal pair: `accepted by the hub`, `overwritten by the hub`
  (rejected and rolled back), `rejected · your newer edit kept` (`superseded`), `verdict
  recorded; live row unchanged` (`unknown-shape`). No label claims publication or subscriber
  visibility (INV-17).

**The app-side drainer is wired** (`sync/inbox.rs`, fired every sync round): it drains
`GET /api/v1/inbox?scope=<dataset uuid>&after=<cursor>` →
`{dataset_uuid, entries[{change_id, proposal_seq, object_id, kind, op, edit_time, author,
payload}], pruned_up_to, inbox_seq, resync_required}`, applies each entry through the normal
card command, then `POST /api/v1/inbox/ack` with
`{accepted:[{change_id, seq}], rejected:[{change_id, winner_seq, winner_payload, winner_kind}]}`
(`seq` is optional, stored for traceability only — the website mints no journal seq, INV-1;
`winner_kind` is optional and narrows the detector rather than replacing it; a `failed` apply is
omitted from both lists, which is why a held cursor and a later re-ack are expected).
`change_id` is the dedup and ack handle; acks are idempotent. Pinned by the
`card_proposal_shape`, `tag_proposal_shape`, `ack_rollback_decision` (pure) and `inbox_ack`
(DB) vectors in `tests/sync_conformance/` — the shape vectors additionally assert that this
host's own journal reader (`sync/change_log.ts::objectIdFor/opFor/changeClassOf`) derives from
each payload exactly what the seam put on the wire.

> Verification note: a harness run against a Postgres that was not reset fails
> `epoch_page_and_enforce` on a `dataset_pkey` collision — `dataset.uuid` is the primary key
> while the per-vector reset cleans by `user_id`, and two older vectors share one fixture uuid.
> That is pre-existing, unrelated to these vectors; always
> `prisma db push --force-reset --accept-data-loss` on the scratch database before a run.

### 6.3 The live-row role gate: only the authority writes a scope's rows directly

§6.2's mirror rule was enforced for cards only. The three remaining row-level writers of a
dataset's live `data.sqlite3` — the dictation cue editor and the two Read-a-Book writers — sat
behind `gateDatasetRead` + `canPushDataset` with **no `journal_role` check**, and nothing but
`EDIT_ENABLED = false` in their UI (`listen/dictation/client.tsx:39`, `speak/read/client.tsx:46`)
kept them dormant. That is now a rule in code rather than a flag in a page:

| action | writer | what it mutates |
| --- | --- | --- |
| `actions/dataset_dictation.ts::saveDatasetDictationCues` | `dictstore.saveCues` | the whole cue set of one subtitle (`DELETE` + re-`INSERT`) |
| `actions/dataset_read.ts::saveDatasetBookSentences` | `bookstore.saveSentences` | `book_sentence` / `book_sentence_word` + `fs.rmSync` of dropped `media/*.wav` |
| `actions/dataset_read.ts::writeDatasetSentenceAudio` | `bookstore.writeAudio` | a new `media/<sentence>.wav`, then the manifest, counters and `snapshot_seq` |

Each one now calls `liveEditRefusal(gated.ds.journal_role)` (`src/lib/sync/handover.ts`, the
role's own module) immediately after the push gate and **before any file or DB mutation**, and
returns the single shared refusal string when it is non-null. The predicate is default-deny:
anything that is not exactly `'authority'` — including `'mirror'` (the column default), `''` and
any value no code has ever written — is refused, so a missing role refuses rather than permits.
`journal_role` was added to `datasetCatalogFields` so `gateDatasetRead` hands the role to the
gates without a second per-request read (the reason `api/card/sync/push` carries its own extra
`select`). The policy deliberately lives at the action layer, not inside
`dictstore`/`bookstore`, which stay file-format modules with no catalog knowledge.

Why this direction and not the card direction: a mirror scope's rows belong to its desktop hub,
and this host's live copy is not a private draft — subscribers download it and the hub pulls it
back through the frozen `getChangesSince` → `/api/card/sync/pull` wire, so an unguarded write
propagates **into** the authority and corrupts it (INV-1). Cards take the opposite shape because
the seam to queue them exists (§6.2); cue and book rows have none yet, so the honest answer today
is a refusal that names both ways forward: edit on the hub, or hand the scope over first.

Two residuals this gate does **not** close, stated so nobody reads it as convergence:

- **No cue/book proposal producers.** `card_proposals.ts` builds only the five card-family kinds;
  `applyDatasetChangeIfStale` has no cue case (its `guardTarget` throws for cue kinds),
  `winnerToApply`/`isCardFamilyKind` exclude cue, and the journal's cue applier is a per-cue
  UPSERT while the editor is a whole-subtitle replace with `order_num` renumbering. Making cue
  edits proposable is §14 phase 8's own work, not a line in this one.
- **An authority-side cue/book write mints no journal entry and no `snapshot_seq` bump** (the
  audio path bumps it only for its own added file). It is visible on this host and to anyone
  reading this host's live copy; it does not converge to a follower through the dataset journal.

`POST /api/dataset/upload` is intentionally outside this rule — see §3.7.

Pinned by the **pure** `live_edit_gate` vector (no DB needed): the decision table, the identity of
the shared refusal, a source-shape pin that each of the three actions gates before its writer call
(a `'use server'` action cannot be imported into the harness), and the pin that `serializeDataset`
still does not emit `journal_role`.

## 7. App-side work items, in order

### T1 — Bearer transport for the website hub origin
Files: `src-tauri/src/sync/client.rs` (`with_device_auth` ~line 219,
`signed_get_json` ~1332, `dataset_sync_snapshot` ~588), `src-tauri/src/auth.rs`.

The hub client today signs every request with device HMAC headers and reads the
base from `pc_base(settings)`. Against `auth::BASE_URL` ("https://lusworkshop.site")
that fails for anything visibility-gated.

Implement a single outbound-request builder that chooses auth by origin:

```
fn hub_request(method, path, query, body) -> RequestBuilder
  if base_of(path) is the website origin:
      .header("Authorization", format!("Bearer {}", get_access_token(settings)?))
  else:
      with_device_auth(...)   // unchanged LAN behaviour
```

Rules:
- Reuse `get_access_token(settings)` from `datasets/cards/sync.rs` (it already
  reads the stored `access_token`); do not add a second token store.
- Refresh/re-login on `401` exactly as `auth.rs` does elsewhere; `403` is not a
  token problem — surface "you cannot access this dataset".
- Do **not** send `x-fms-*` headers to the website (harmless, but a future
  strict-mode route would reject unknown signing headers).
- Keep the LAN path byte-identical; the website path is additive.
- `hub_cluster_id` / `hub_protocol_version` / pairing calls must be skipped for a
  website origin (§6).

### T2 — `dataset_export_upload` command (the app can only pull today)
There is **no** export/upload in the app. Add a Tauri command:

1. Open the dataset dir `<datasets>/<type>/<uuid>/`.
2. Freeze the DB: `conn.backup()` into a temp file, and write the frozen copy
   into the pack stage **as `data.sqlite3`**; never include `-wal`, `-shm` or
   `fts5.sqlite3*`.
3. Refresh `info.json` before packing: `updated_at` = `canonical_stamp(now)` in
   the second-precision `YYYY-MM-DDTHH:MM:SSZ` form (this becomes the hub's
   `updated` / `manifest.updated_at`), plus current `name/description/language`.
   Leave `sharing.*` as-is (ignored server-side, §4.3).
4. Pack `tar.gz` with rel-path entries at the archive root (no top-level dir) —
   matching §3.3 so the hub can accept either layout.
5. `POST /api/dataset/upload` with `file` (+ optional `visibility`, `tag_uuids`),
   Bearer auth (§T1), streaming with progress reported to the UI.
6. On `409`: the uuid belongs to someone else — offer "save as new uuid"
   (regenerate uuid, rewrite `info.json.uuid` **and** rename the dir + any
   `source_dataset_uuid` references), do not silently overwrite.
7. After a successful upload, record `version`/`archive_sha256` locally so the UI
   can show "this copy is uploaded".

Do **not** attempt to fake the upload by shipping a snapshot: the snapshot tar
has no top-level dir either, so it *is* a valid upload body, but the upload path
re-hashes the live dir server-side — shipping a stale DB is exactly how you get a
follower a snapshot whose rows lag your own. Freeze the DB (step 2) always.

### T3 — Feature-detect the website hub
Before a round, decide origin capability once (a `HubKind { Website, LanPc }`
enum on the resolved base URL) and gate: journal/`app/state` pulls,
pairing/cluster/protocol calls, chat and wiki hub browsing (§6). Card sync and
file sync run for both kinds.

### T4 — Sync-round wiring for a website origin
`sync_round_inner` / `dataset_sync_snapshot` should, for `HubKind::Website`:
`GET /api/v1/datasets?lite=1` → diff against local `dataset_sync_state` by
`overall_hash` via `GET .../manifest` → `GET .../snapshot` for changed dirs
(record `x-snapshot-hash`, `x-snapshot-seq`) → card datasets additionally run the
existing `cards/sync.rs` round.

**Subscribing is not available to the app.** `dataset_subscription` rows are
written only by the browser-only server actions in
`src/app/actions/dataset_hub.ts` (`subscribeDataset` / `unsubscribeDataset`);
there is no REST route for them, so a `shared` dataset simply does not appear in
the app's `?lite=1` list until its owner subscribes the account from the website
market page. If the app needs in-app subscribe, that is a new website endpoint —
request it, do not call the server action over HTTP.

### T5 — Card-sync cursor and conflict hygiene
`sync_state.last_synced_at` must persist the `server_time` text verbatim
(already canonicalized by your `update_sync_state`). Verify §8.6 items. Treat
`conflicts[].winner == "remote"` as "remote row is authoritative, refetch it" —
merge it into local on the next pull instead of pushing again.

### T6 — Media streaming via `/api/v1/file`
Use Range requests for playback/resume against the website (§3.4); never fetch
`data.sqlite3` through `/file` (it is 403 by design and must stay that way —
rows go through card sync).

### T7 — Error surface
Map website error bodies to app messages without losing the code: 401 → "sign
in", 403 → "no access / key is read-only", 404 → "not on this hub", 409 →
ownership/type conflict (§3.7), 413 → "too large, see limits", 5xx → retry with
backoff.

### T8 — Version pin
Record in your hub client which contract version this doc describes, and refuse
to silently accept a new field name. The list/manifest/snapshot/card-sync field
names in §3 are the wire contract; renaming one breaks the other side.

## 9. Deployment caveats (website side; relevant when you test against prod)

- `/fms_datasets` is a **separate mount** (`deployment.yaml` hostPath
  `/wsva/data/fms_datasets`) and must never live under `/fms_data`:
  `src/app/api/data/[...filename]` serves `/fms_data` to any authenticated caller
  with no visibility gate, which would leak private datasets.
- nginx `client_max_body_size` is currently **50m** while the app allows 512 MB;
  uploads above 50 MB fail at the proxy (413 from nginx, not from Next.js). Raise
  it before testing large datasets.
- Schema change `20261013000000_add_dataset_hub` is applied with
  `psql -f <migration>.sql` + `prisma migrate resolve --applied …`. **Do not** use
  `prisma db push` on production (the local `schema.prisma` omits six prod-only
  tables and `db push` would drop them) and **do not** use `migrate deploy`
  (already-applied unrecorded migrations would be replayed).
- Card pushes serialize behind an in-process lock: a single Next.js instance is
  assumed. A multi-instance topology needs a shared lock or single-writer
  routing before concurrent pushes are safe.

## 10. Rules for the implementing agent

1. The contracts in §3 and the recipe in §4.1 are frozen. Implement to them; if
   you believe one is wrong, report it with the observed payload — do not
   unilaterally change the hash, the header names, or the field names.
2. Never write to website Postgres directly; the catalog is derived from uploads.
3. Never rely on `info.json.sharing` for access decisions — always ask the hub
   (the visibility gate) or accept its 403.
4. Keep the LAN (`HubKind::LanPc`) request path byte-identical; the website path
   is additive. Existing device-HMAC pairing must not regress.
5. Any new app-side state lives in the app DB, not in the dataset directory
   (§4.2).
